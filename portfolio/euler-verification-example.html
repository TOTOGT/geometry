Euler’s 1747 conjecture: what a green check does and does not say

A new paper claims that every integer n ≡ 2 (mod 4) is a sum of two positive integers whose prime factors are all ≡ 1 (mod 4). We tried to check it in Lean. This page records what was run, what each run showed, the mistakes we made and caught on the way, and the one place where a clean-looking result is not what it seems.

Short version. The finite range (every such n < 644) is checked by computation, and the full conjecture is reduced to one hypothesis, the paper’s Proposition 6.1, which we did not prove. Our file is not the paper’s formalization and is not a proof of Euler’s conjecture.

Update, 17 Nov. Most of that Proposition’s elementary skeleton (paper sections 4 to 6) is now kernel-checked in Lean, so the single hypothesis has shrunk to three named ones: the spectral bound of Proposition 3.1 (which needs the open Lemma 3.2), a count of two-square representations, and Jacobi’s four-square formula. Still conditional; still not a proof of the conjecture. Details below.

Still open, in order of size. Lemma 3.2 and hence Proposition 3.1 (needs Jacquet–Langlands and a weight-2 Ramanujan–Petersson bound, neither in Mathlib); Jacobi’s four-square count; the two-square count r2(u) ≤ 4·M(u), for which a computer check up to 20,000 found no violation and which is tight in 5,258 of those cases (a sanity check, not a proof; produced by tools/r2_bound_check.py). The paper’s finite range (Proposition 7.2) is the part already done above.

What a reader should not take from this. Nothing here shows Proposition 6.1 holds. The 0.6458 figure is the paper’s arithmetic, now machine-checked, applied to a bound we assumed.

The trap in the second line

The conditional theorem prints the same clean axiom list as the finite one. That does not mean the conjecture is proved. AnalyticRange enters as a hypothesis argument H, and #print axioms lists axioms, not hypotheses. Reading the theorem’s statement, not its name or its axiom list, is what shows it is conditional.

Mistakes caught along the way

  1. A green run that tested nothing. An existing CI workflow (“Verify Lean proofs”, run #981) went green on the commit that added the Euler files. It cannot have compiled them: EulerLean/ was not a build target. Only the separate manual workflow checks these files.
  2. Wrong tactic cases. The first compile failed with Invalid alternative name h0: the induction principle’s cases are zero | one | prime | mul in the current Mathlib. Fixed against the compiler’s message.
  3. Two errors in the four-square file. Finset.Icc on the integers picked a noncomputable instance, so R had to be marked noncomputable and its #eval dropped. A simp left x 3 + x 2 against x 2 + x 3; omega closed it.
  4. A wrong performance guess. We guessed the 4-million-case proof would take hours. A timing test on the first 20,000 cases took 471 ms, which put the lower bound near 99 s. The real run took about 11 minutes, because later cases need many more trial divisions. Measure before predicting.
  5. A monitor that watched the wrong word. The workflow was written to warn if Lean.ofReduceBool appeared. In this Lean version native_decide shows up as …native_decide.ax_1_1, so the warning never fired. The check was fixed to match both names.
  6. Terminal output pasted as commands. A block of expected output was pasted into a shell, producing harmless command not found errors. Output and commands should not look alike.
  7. Wrong closing steps, found by the compiler. One lemma ended with a subset lemma where the goal asked for membership in a different set; another used a lemma name deprecated in this Mathlib and expecting ≠ 0. Both were fixed against the error text.
  8. A tactic that finished early. After field_simp closed a goal, the following ring failed with “No goals to be solved”; the fix was try ring. Two runs failed on this before it was fixed.
  9. A floor-division trap, found in review before any run. A planned recursion for the two-square count wrote u / q²; at u = q that is 0, and the set for 0 contains the point (0,0), so the formula would have counted a phantom solution. The recursion is stated without division.

What we did not do

We tested the paper’s analytic sections (2–6) numerically and by hand reading, instance by instance, and put the elementary part of sections 4 to 6 into Lean (see the 17 Nov update), but we did not prove the spectral part, so we cannot say Proposition 6.1 is proved; Lemma 3.2 needs results (Jacquet–Langlands, Deligne) that are not in Mathlib. We did not reproduce the paper’s own formalization, and this file is an independent partial attempt, not a check of theirs. A passing run only counts for the files it compiled, and only to the trust level of the axioms it printed.

The method, in five lines

  1. Derive the math by hand first; write the Lean second; mark it untested in the same sentence as the claim.
  2. Run it against a real kernel, and fix against what the compiler says, not what we expect.
  3. Print the axioms for every theorem and read each theorem’s statement, not its name.
  4. Label the trust level in words: kernel-checked, compiler-checked, or conditional.
  5. Say what the run did not cover before anyone else has to ask.
