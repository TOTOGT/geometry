Capstone

From problem statement to evaluation and reflection: a framework for the proposal, implementation plan, final project and report.

How to use this chapter

I'm writing these chapters while I work through the MSIT at University of the People, so that you and I can study from the same page. Each one follows the course's official unit list, explains the standard ideas behind each unit in my own words, and ends every unit with a self-check question you can use to test yourself. It does not contain answers to graded assignments, and it does not replace the course readings. Write your own work in your own words. I'm doing the same with mine. Unit 1 · Project Proposal: Part 1

The capstone applies what the program taught to a real or realistic business problem. A proposal starts with the problem: who has it, what it costs them, and how you know. State a problem statement in a few sentences, define the stakeholders, and write objectives that are specific and measurable, because the solution is later evaluated against them. A weak objective is “improve the process”; a strong one names a metric and a target, such as reducing average ticket resolution time from 3 days to 1 day.

Scope the project so it can be finished in the term. Say what is in, what is out, and what you assume.

Self-check Rewrite the objective “make the app better” as one measurable objective with a metric, baseline and target.

Unit 2 · Project Proposal: Part 2

The second half of the proposal justifies the approach. Review credible sources on the problem and on candidate technologies, compare two or three alternatives against criteria, and give a reasoned recommendation. A simple weighted decision matrix makes the comparison explicit: list criteria, weight them, score each option, and sum. Show the arithmetic and say how sensitive the result is to your weights. Identify risks (technical, schedule, data, ethical) with a likelihood, an impact and a response.

The program outcomes require arguments supported by credible, relevant sources. Cite them in the required style, and prefer primary and peer-reviewed material to blog posts.

Self-check List three criteria for choosing between a cloud database and an on-premises one, and give each a weight with a reason.

Unit 3 · Project Implementation Plan: Part 1

Turn the proposal into a plan. Analyze user needs: interviews, surveys, personas and use cases, then turn them into requirements, each testable and traceable to an objective. Separate functional from non-functional requirements and decide priorities (for example must, should, could). The outcomes list user-needs analysis explicitly, so the plan should show the evidence for each requirement, not just assert it.

Self-check Write two requirements, one functional and one non-functional, each with a way to test it.

Unit 4 · Project Implementation Plan: Part 2

Design the solution. Describe the architecture with a diagram, the main components and data, and the technologies chosen and why, drawing on the design and database chapters of this book. Explain how the design meets each requirement and which quality attributes (security, performance, usability) drove choices. Note constraints such as budget, skills and existing systems, and show how you will manage them.

Self-check Draw a block diagram of your intended solution with at most six components and label what each requirement maps to.

Unit 5 · Project Implementation Plan: Part 3

Plan the work. Break it into tasks (a work breakdown structure), estimate durations, sequence dependencies and find the critical path, as in the project chapter. Assign effort realistically, include time for testing and revision, and keep a buffer. Add a risk register and a communication plan. Choose a delivery method, often iterative, with milestones that show working increments.

Self-check Take five tasks with durations and dependencies and compute the critical path length.

Unit 6 · Project Implementation Plan: Part 4

Plan how you will know the solution works. Define a test plan: what is tested at unit, integration and acceptance levels, with what data, against which acceptance criteria. Define an evaluation plan that returns to the proposal's objectives: which measurements, compared with which baseline, and what result would count as success or failure. Address ethics: privacy, bias, accessibility, consent and security, and what you will do about each. The outcomes name ethical analysis explicitly.

Self-check For one objective of your project, state the measurement, the baseline, the success threshold and one ethical risk.

Unit 7 · Final Project Due

Implement the feedback you received on earlier submissions, finish the artifact and the written report, and prepare the presentation. A strong report has a clear structure: summary, problem, objectives, approach, design, implementation, evaluation against the objectives, ethics, limitations, and conclusion. Report negative or partial results honestly; an evaluation that admits what did not work is better than one that claims everything succeeded. Check every claim has evidence or a citation.

Present for your audience. A short talk states the problem, shows the solution working, gives the evaluation result and ends with what you would do next.

Self-check Write the one-sentence takeaway of your project that a non-technical stakeholder should remember.

Unit 8 · Capstone Report Submission

The last unit is the capstone reflection. Reflect on what the program and the project taught you, what you would do differently, how your skills map to the program outcomes, and what you will learn next. Use specific examples: a decision that turned out wrong and what you learned, a technique you applied from a particular course. Reflection is judged on honesty and evidence, not on praise for yourself or the program.

Self-check List three program courses you drew on and one concrete decision where each mattered.
