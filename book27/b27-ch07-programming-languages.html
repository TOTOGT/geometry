Unit 1 · Programming Language Introduction

A programming language is defined by syntax (which strings are programs), semantics (what programs mean) and a pragmatics of style and tooling. Paradigms group languages by how they organize computation: imperative and procedural (change state step by step), object-oriented (objects with behavior), functional (functions as values, little mutation) and logic (relations and search). Most real languages mix them. Implementations are compiled to machine code, interpreted directly, or run on a virtual machine; the same language can be implemented several ways.

Self-check Pick one language you know and place it among the paradigms. Name one feature it takes from a different paradigm.

Unit 2 · Building the Programming Foundation

Source text is turned into structure in stages. A lexer groups characters into tokens; a parser builds a tree following a grammar; later passes check and evaluate. A grammar encodes precedence by layering rules: expressions are sums of terms, terms are products of factors.

Worked example computed. The string 2 + 3 * (4 - 1) tokenizes to 2 + 3 * ( 4 - 1 ). A recursive-descent parser for the grammar expr → term (+|- term)*, term → factor (*|/ factor)*, factor → number | ( expr ) builds the tree (+ 2 (* 3 (- 4 1))), and evaluating it gives 11. Multiplication binds tighter because it sits one level deeper in the grammar, and the parentheses force 4 - 1 to be evaluated first.

Self-check Draw the tree for 8 / 4 / 2 under the grammar above and say whether it groups to the left or right, and what that gives.

Unit 3 · Functions

A function maps arguments to a result. Under lexical (static) scope a name refers to the nearest enclosing definition in the source text; under dynamic scope it refers to the most recent binding at run time. Most modern languages are lexically scoped. When functions are first-class values you can pass and return them, and a closure is a function packaged with the environment in which it was created. Higher-order functions such as map, filter and reduce abstract common loops; recursion replaces iteration, and tail calls let a compiler reuse the stack frame.

Self-check Write a function make_adder(n) that returns a function adding n, and say which variable the closure captures.

Unit 4 · Variable, Objects, and Mutation

A variable names a location; assignment changes what is stored. Mutation makes behavior depend on history, and aliasing, two names for one object, makes a change through one name visible through the other. Equality has two meanings: equal value versus the same object.

Worked example computed. A closure over a mutable counter: make() returns inc that does n += 1 and returns n. With a = make() and b = make(), the calls a(), a(), b(), a() return 1, 2, 1, 3. Each call to make creates its own environment, so a and b do not share n, but successive calls to a do share theirs. Objects bundle state with behavior; inheritance and composition are two ways to reuse it, and many designs favor composition.

Self-check Explain why the third call returns 1 and not 3, in terms of environments.

Unit 5 · Memory, Errors, and Design

Memory is managed manually (allocate and free), by ownership rules enforced at compile time, or by a garbage collector that reclaims unreachable objects. Manual management risks leaks, dangling pointers and double frees; collection costs pauses and overhead. Stack frames hold locals and return addresses; the heap holds objects with flexible lifetimes.

Errors are handled by return codes, exceptions or result types. Exceptions separate the error path from the main logic but can skip cleanup unless the language has finally or scope-bound resources. Good design hides representation behind a stable interface (abstraction and information hiding) and keeps modules loosely coupled.

Self-check Describe one bug that is possible in manual memory management and impossible with garbage collection, and one cost of the latter.

Unit 6 · Control Structures and Type Systems

Control structures choose and repeat: conditionals, loops, pattern matching, exceptions, coroutines. A type system classifies values to rule out meaningless operations. Static typing checks before running and dynamic typing checks while running; strong typing refuses silent unsafe conversions, while weak typing coerces. Type inference lets a compiler deduce types you did not write. Parametric polymorphism (generics) writes code once for many types; subtyping lets a value of a more specific type stand in for a general one.

Static and strong are separate axes: a language can be dynamic and strong (Python) or static and weak (C). The trade is early error detection and tooling against flexibility and brevity.

Self-check Place Python, C and Java on the static/dynamic and strong/weak axes and justify one placement.

Unit 7 · Evaluation and Lazy Evaluation

An evaluation strategy says when an argument is evaluated. Call by value evaluates it before the call; call by name substitutes the unevaluated expression, re-evaluating at each use; call by need (lazy evaluation) evaluates at first use and caches. They agree on the answer when evaluation has no side effects and terminates, but not on cost or on termination: laziness can skip an argument that would diverge or fail.

Worked example computed. Let f(x) = x + x applied to an argument expression that is expensive and returns 21. All three strategies return 42. Counting evaluations of the argument: call by value 1, call by name 2, call by need 1. Laziness lets you define infinite lists and pay only for what you consume, at the price of harder reasoning about time and space.

Self-check Give an example where call by value loops forever but call by name returns an answer.

Unit 8 · Preparation for the Final Project

The course ends with a working language prototype. A manageable design is a small expression or command language with a lexer, a recursive-descent parser that builds a tree, and an evaluator that walks it, as in Unit 2 extended with variables, functions and one clear semantic choice (scope rule or evaluation strategy). Specify the grammar first, write tests from examples of valid and invalid input, and keep each stage separately testable.

The outcomes also ask you to justify choosing one language over a similar one for an organization, and to examine limits through ethical and historical lenses. Write the justification in terms of requirements: team skills, performance, safety, libraries and maintenance cost. This chapter does not supply a prototype or a justification for your assignment.

Self-check Write the grammar, in the notation of Unit 2, for a language of integer assignments and sums such as x = 1 + 2.
