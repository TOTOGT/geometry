When Lean refuses a proof, the complaint comes from one of a few programs in a pipeline, and each program has a different contract with you. Ullrich's dissertation draws the pipeline. This chapter sorts this corpus's own failures by the layer that raised them, and in almost every case the fix belonged to a different layer than the one that complained.
1 · The pipeline

Parser, macro expansion, elaborator, kernel

Ullrich's Fig. 3.1 (p.34) runs input through the parser, macro expansion and the elaborator, and then hands the result to the kernel. The core language output "is then checked by the kernel (Section 3.2), which is an independent component in order to minimize the Trusted Code Base" (p.34). CITED

The division of labour follows from that. Everything before the kernel may be clever, large and wrong. The kernel must be small and right. Ullrich says it plainly about tactics: "metaprograms are not part of Lean's Trusted Code Base — after execution, their output is checked by the kernel just as if we had written down the output manually" (p.15). CITED

The consequence for a reader A tactic cannot make a false theorem true. It can only fail to produce a term, or produce one the kernel rejects. What a reader must trust is the kernel, plus whatever extra axioms a proof admits, and #print axioms reports those.
2 · Three facts from the source
  • "The Lean kernel does not accept any kind of recursion in regular definitions; recursion is instead transformed by the frontend into applications of recursors" (p.15). A recursive definition you write is not the term the kernel sees. CITED
  • "The kernel type checker does not use a metavariable context and will reject remaining metavariables" (p.19). A hole the elaborator could not fill never reaches the kernel as a hole. CITED
  • Natural-number literals are computed by an arbitrary-precision library, "which therefore becomes part of the Trusted Code Base" (p.36). Even the small kernel trusts some fast arithmetic. CITED
